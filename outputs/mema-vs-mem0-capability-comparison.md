## 一、先说结论

如果一定要问“谁更好”，不能只问谁的刀更快，还要问是在厨房切菜，还是在手术室动刀。

- **做通用 AI 产品、面向多种技术栈、追求快速接入和大规模召回：mem0 更好。** 它的连接器更多、向量库更多、模型适配更多，召回算法更完整，公开基准更成熟。它像一座已经通车的“记忆中台”：入口多、道路宽、车辆多。
- **做本机个人记忆、强调事实可控、冲突可审、修改可追、AI 不得擅自改口：mema 更好。** 它把工作区、证据、冲突单、授权闸门、版本历史、修复任务做成了一套治理系统。它像一位谨慎的“档案馆管家”：不只帮你找到材料，还会告诉你哪份过期、哪两份打架、谁有权改。
- **若必须脱离场景，只选一个“综合产品能力更强”的：我选 mem0。** 原因不是用户多，而是它在通用接入、存储适配、检索算法、公开标准评测和生产部署形态上更完整。
- **若限定为“咱们当前这个本地、跨 Agent、个人事实库”的目标：我选 mema。** 因为这里最难的不是“搜到一句相似的话”，而是“别串项目、别悄悄覆盖、别把冲突当真相、改错还能追”。这几件事正是 mema 的主航道，而不是 mem0 OSS 的主航道。

一句话概括：**mem0 更像记忆发动机，mema 更像记忆治理系统。发动机决定跑得快不快，治理系统决定会不会跑错路。**

## 二、两者其实不是完全同一种产品

### mem0 在解决什么

mem0 的中心问题是：**怎样从对话里抽出值得记住的事实，并在以后又快又准地找回来。**

它的 2026 新算法很明确：一次 LLM 抽取，只做 ADD，不自动 UPDATE/DELETE；事实不断累积，再靠语义、BM25 关键词、实体链接和时间信号做混合召回。源码中，写入链路是“找已有记忆 → 一次 LLM 抽取 → 批量 embedding → 哈希去重 → 写向量库 → 记录历史 → 实体链接”；搜索链路是“语义搜索 + 关键词搜索 + 实体加权 → 融合排序”。

### mema 在解决什么

mema 的中心问题是：**当多个 AI 客户端共用一套长期记忆时，怎样让事实有出处、有边界、有版本、有裁决。**

它不是只做 `remember/find`，而是拆成四个面：日常读写、只读审查、授权治理、运维修复。写进去以后，还要管工作区、证据单元、版本、相似项、冲突候选、正式冲突、用户确认、备份回放和索引修复。

所以，两者像两家医院：

- mem0 更擅长“挂号快、科室全、检查设备多”；
- mema 更擅长“病历不能乱改、会诊意见要留痕、手术必须授权”。

## 三、能力地图

```text
                         AI 长期记忆能力地图

          接入广度 / 生态 / 横向扩展
                      ↑
                      │            mem0
                      │      ● 多 SDK、多模型、多向量库
                      │      ● 混合召回、实体增强
                      │      ● 自托管服务 + 云平台
                      │
  简单存取  ←─────────┼─────────→  强治理
                      │
                      │                    mema
                      │              ● 冲突生命周期
                      │              ● 授权修改、版本审计
                      │              ● 工作区隔离、修复工具
                      │              ● 本地 SQLite + 本地模型
                      ↓
              本地可控 / 个人事实安全
```

这张图不是说 mem0 没治理，也不是说 mema 没检索，而是说两者把“最贵的研发预算”花在了不同地方：**mem0 把钱花在路网，mema 把钱花在交规。**

## 四、逐项对比

| 能力 | mem0 | mema | 更强者 |
|---|---|---|---|
| 对话事实抽取 | 一次 LLM 调用，证据约束、ADD-only；支持用户/Agent/会话作用域 | 主要由 Agent 显式写入，强调原文保存、证据化和标签 | mem0（自动抽取） |
| 检索 | 语义 + BM25 + 实体加权，可选 reranker；托管版另有时间推理 | FTS + 本地向量 + 词法锚点 + 页面阈值；支持命中片段、outline、分段读取 | mem0（算法广度）；mema（可解释交付） |

| 本地与隐私 | OSS 可自托管；默认仍依赖 LLM/embedding provider，也可接本地模型 | SQLite、本地 GGUF embedding、本地 Qwen 冲突判断；默认 localhost | mema（默认姿态） |

## 五、最关键的设计分歧

### 1. mem0 选择“多记，少改”；mema 选择“可改，但必须过闸”

mem0 2026 算法改成 ADD-only：旧事实不覆盖，新事实继续加。好处是写入简单、调用少、历史不丢；代价是同一对象的多个状态会并存，最终依赖检索算法把“当前那条”挑出来。

mema 则把“哪条是当前真相”当成治理问题。它允许 supersede、merge、resolve，但有授权门、版本检查和审计记录。好处是事实状态更清楚；代价是系统更重，Agent 和用户要理解更多状态。

白话说：

- mem0 像往文件夹里不断加新纸，取用时让检索员挑最新最合适的一张；
- mema 像档案馆盖“现行、废止、冲突、待确认”章，盖章前还要走审批。

前者轻，后者稳；前者适合高吞吐，后者适合高责任。

### 2. mem0 把智能放在抽取与排序；mema 把智能关在护栏里

mem0 让 LLM 负责从对话抽事实，之后用多信号排序。mema 更强调“模型只能建议，不能擅改”：本地小模型发现冲突后，只能发通知或进入队列，真正修改必须由授权治理面执行。

这不是谁更先进，而是风险偏好不同：

- 客服助手记住“用户喜欢深色模式”，自动一点更舒服；
- 工作 Agent 记住“生产库允许删除”，自动一点可能就更危险。

### 3. mem0 的优势是“换零件”；mema 的优势是“看账本”

mem0 的 provider/factory 体系很强：模型可换、向量库可换、reranker 可换，像一台标准接口的工业设备。

mema 的审计和修复面更强：冲突从哪里来、证据在哪一段、索引有没有积压、谁改过哪一版，都能查，像一本不允许撕页的账本。

## 六、测试数据怎么读，哪些能比，哪些不能比

### mem0 的公开成绩

mem0 README 报告的新算法成绩为：

- LoCoMo：92.5
- LongMemEval：94.4
- BEAM 1M：64.1
- BEAM 10M：48.6
- 单次召回、top-200 预算，约 6.7K—7.0K tokens，p50 约 0.88—1.09 秒

但必须把脚注读完：**这些分数来自 mem0 托管平台，包含开源 SDK 没有的专有优化。** 因此可以证明 mem0 团队的算法和评测成熟，但不能直接写成“开源 mem0 本地安装就是 94.4”。

### mema 的近期实测

mema 0.16.6 基线使用 98 个目标、200 个干扰项：

- Recall@5：37/45，82.22%
- Recall@10：43/45，95.56%
- MRR：0.797（19 个带目标查询）
- 自召回 Top10：97/98，98.98%
- 无关误拉：7/21，33.33%

页面阈值专项对 340 个候选做了人工盲标。在 8.08 附近的阈值下，切掉 73% 无关项、91% 域外噪音，误切 4/45 相关项。更重要的是，评测推翻了原先“按向量距离幅度分级加分”的设计判断：相关和无关的距离高度重叠，真正拉开差距的是词法锚点与融合分。这说明评测不是只为报喜，也在负责“叫停错误方向”。

工作区归位专项中，清晰桶 28/30，准确率 93.3%；对照项 13/15 保持不动，86.7%。报告也没有粉饰：跨项目的元内容仍然是弱点，尚未达到可以完全自主搬动的程度。

冲突基线更需要诚实：精确率 3/4=75%，召回率 3/22=13.64%。也就是说，**报出来的冲突多数是真的，但漏掉的真冲突还很多。** 这条链路的产品设计很完整，检测效果却仍在爬坡。

### 为什么不能拿 94.4 和 95.56% 直接比

因为分母不同、任务不同、模型不同、语料不同、检索预算不同。一个像高考总分，一个像驾驶证路考通过率，数字都接近 95，不代表是一回事。

因此，以下说法目前**暂不可对外声明**：

- “mema 召回准确率高于 mem0”；
- “mem0 在本地个人事实库上一定优于 mema”；
- “mema 的冲突判断整体优于 mem0 的时间推理”。

要证明这些，必须用同一批语料、同一问题、同一 LLM、同一 embedding、同一 top-k 做 head-to-head 双跑。

## 七、各自真正的短板

### mem0 的短板

1. **开源与托管能力边界容易被忽略。** 最亮眼的时间推理和 benchmark 数字属于托管平台；OSS 源码对 `timestamp`、`reference_date` 会明确提示平台专属。
2. **ADD-only 把一部分一致性难题推给了检索。** 不覆盖更安全，但长期累积后，旧状态、现状态、计划状态都在，排序错一次就可能答错一次。
3. **普通 history 不等于治理。** 有 ADD/UPDATE/DELETE 记录，不代表有冲突单、授权计划、版本钉死、误报抑制和修复队列。
4. **默认链路离不开模型和 embedding。** 可以本地化，但需要自己搭配 provider；“安装 SDK”不等于“天然完全离线”。

### mema 的短板

1. **生态窄。** 目前是本地 SQLite 路线，缺少 mem0 那种广泛的向量库、模型和语言 SDK 适配。
2. **多人生产服务能力不足。** localhost HTTP 的身份头不是认证，不是多租户隔离；不能直接当企业共享记忆 SaaS。
3. **治理链复杂。** 状态、队列、扫描、授权动作多，Agent 用错动作的概率也会上升。它像专业相机，能力强，但不是拿起就拍。
4. **冲突检测召回仍低。** 13.64% 的基线说明“完整生命周期”已经有了，但“把冲突都找出来”还远未完成。
5. **标准评测不足。** 当前数据贴近真实使用，但样本量较小、部分为人工或半自动实验、不是持续 CI benchmark，无法直接支撑行业级性能宣传。
6. **“本地优先”不等于物理断网。** 核心模型和数据可本地运行，但更新检查默认可能访问 PyPI；更准确的说法是 local-first，而不是强制 air-gapped。

## 八、最终判断

### 作为通用产品，mem0 胜

它胜在五个“更”：

- 接得更多：语言、模型、向量库、框架更多；
- 跑得更远：从库、服务器到云平台，部署路径更完整；
- 搜得更广：语义、关键词、实体、托管版时间推理多路并进；
- 证得更标准：有 LoCoMo、LongMemEval、BEAM 和公开评测框架；
- 交得更快：开发者更容易把它塞进一个新产品。

### 作为本地个人事实基础设施，mema 胜

它胜在五个“更”：

- 边界更清：workspace 不是随手贴标签，而是可审查的项目抽屉；
- 修改更慎：模型能发现问题，不能越权改事实；
- 冲突更显：不是把矛盾埋在一堆向量里，而是变成可处理的单据；
- 证据更细：命中片段有原文坐标，版本和操作有账可查；
- 修复更全：doctor、扫描、重建、回放、清理组成了维护闭环。

### 我的选择

**不带场景、按综合能力：mem0。**

**带上“本地、个人、多 Agent 共用、事实不能乱改”这个真实目标：mema。**

这并不矛盾。瑞士军刀比保险柜用途广，但保管合同，仍应选保险柜。mem0 是更成熟的通用记忆底座；mema 是更有性格、更重治理、也更贴合本地高信任场景的产品。

mema 下一阶段不该照着 mem0 抄成“另一个通用 SDK”。更合理的方向是：**借 mem0 的长板补检索、补生态、补标准评测；守住自己的长板做冲突、做授权、做证据、做本地治理。** 不和高速公路比车道数量，要把“不会把你带上错路”做成真正可验证的优势。

## 九、建议的同场双跑（按成本从低到高）

1. **低成本：同库检索对照。** 从现有 98 个目标、200 个干扰项导出等价语料，同时写入 mem0 OSS；固定 embedding、top-k 和查询，比较 Recall@5、Recall@10、MRR、无关误拉和 token。
2. **中成本：状态变化集。** 构造“以前住北京、现在住上海”“计划周五上线、后来延期”等 100 组时间状态，比较谁更稳定地回答当前、过去和计划。
3. **中成本：冲突治理集。** 不只测“能否发现冲突”，还测误报抑制、裁决后是否复发、历史能否解释、并发修改是否安全。
4. **高成本：真实 Agent 回放。** 把脱敏后的多会话工作流双写 2—4 周，比较错误记忆造成的任务损失，而不是只比较相似度分数。

双跑完成前，最稳妥的对外表述是：**mem0 的通用召回与生态更成熟；mema 在本地记忆治理、冲突处置和授权审计上设计更深入。**
