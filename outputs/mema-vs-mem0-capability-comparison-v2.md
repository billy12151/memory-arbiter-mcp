## 一、结论先行

上一版报告把“支持更多模型、更多向量库、更多部署方式”当成了 mem0 的主要优势。这把**货架长度**误当成了**药效**，把“能接上”误当成了“接上以后仍然准确、稳定”。这个评价框架不成立，原结论撤回。

重新按用户真正关心的五件事评估：

1. 会不会写入错误事实；
2. 发现事实打架后怎么办；
3. 长文里的关键信息会不会丢；
4. 换模型、换存储后质量是否仍然稳定；
5. 多人使用时能不能隔离、授权、审计；

**我的新判断是：排除用户数量，若把“长期记忆的正确性、稳定性和可治理性”放在第一位，mema 整体设计优于 mem0。**

mem0 更像一台高吞吐的“记忆收纳机”：入口多，放得快，找得快；mema 更像一套“可信档案系统”：写入时查重查冲突，平时定期盘库，发现矛盾后留下证据、进入队列、授权裁决、保留历史。

两者最根本的差异不是功能多少，而是对错误的态度：

- mem0 的主思路是：**先都记下来，召回时再选。**
- mema 的主思路是：**允许不确定，但不允许冲突悄悄混成真相。**

如果记忆只是为了让聊天更贴心，mem0 的轻快很有价值；如果记忆会影响工作判断、生产操作、客户口径或多个 Agent 的后续行动，mema 更可靠。

## 二、这次比较的尺子换了

不能再按“适配器数量”打分，而要按记忆系统的真实事故链打分：

```text
用户说了一句话
      │
      ▼
系统是否抽对了？ ──否──→ 错误事实进入数据库
      │是                    │
      ▼                      ▼
是否与历史冲突？       以后召回时可能被选中
      │                      │
      ├─没检查───────────────┘
      │
      ├─只检查少量候选──→ 可能漏检，需要定期扫描兜底
      │
      ▼
发现冲突以后：覆盖？并存？提醒？裁决？审计？
```

真正决定产品可靠性的，不是第一步能不能写，而是整条链有没有兜底：

- 写错了能不能发现；
- 当场没发现，之后能不能补扫；
- 扫出来以后，机器能处理到哪一步；
- 机器没把握时，能不能把问题交给用户；
- 处理之后，能不能解释谁改了什么、为什么改。

按这把尺子，mema 的设计深度明显更高。

## 三、mem0 的 ADD-only：优点真实，但风险更大

mem0 2026 新算法强调单次抽取、只 ADD、不自动 UPDATE/DELETE。官方给出的理由是减少调用、降低覆盖风险、保留历史。

这确实解决了一个问题：**模型不会因为一次误判，直接抹掉旧事实。**

但它没有解决“哪个事实是真的”，只是把问题往后推了：

- 用户最新说的话可能是口误；
- Agent 最新写入的内容可能是总结错误；
- 抽取模型可能把假设句当事实；
- 转述、引用、反例可能被误记成用户立场；
- 一个错误的新事实可以与正确旧事实长期并存。

于是系统从“写入时可能改错”，变成“每次召回时都可能选错”。

这像一个档案员为了避免撕错文件，决定以后什么都不作废：旧地址留着，新地址留着，写错的地址也留着；每次寄信时，再让另一个模型猜该用哪个地址。

所以 ADD-only 应被中性评价为：

| 方面 | 收益 | 代价 |
|---|---|---|
| 写入效率 | 少一次或多次决策调用 | 错误事实直接积累 |
| 历史保留 | 不会静默覆盖旧事实 | “历史”与“错误”混在同一活动集合 |
| 工程简单度 | 写路径更短 | 复杂度被转移给每一次检索 |
| 当前状态回答 | 可用时间/实体信号排序 | 排序错一次，答案就错一次 |
| 可解释性 | 可查到多条历史事实 | 缺少正式冲突、裁决和现行事实状态 |

**多记少改不是天然优势。它是“用检索概率替代事实治理”的设计选择。**

## 四、mema 写入冲突检测：不是附加功能，而是最难的核心能力

### 4.1 为什么它难

写入冲突检测要同时满足三件互相拉扯的事：

- **快**：用户写一条记忆，不能等系统扫描整个数据库；
- **准**：不能把“同一主题的连续记录”都报成冲突；
- **广**：历史矛盾可能藏在数百、数千条记忆、数万个证据单元里。

全库两两比较的成本会近似平方增长。1,000 条记忆不是比较 1,000 次，而是理论上接近 50 万对；如果每条又拆成多个证据单元，组合数量更大。更不可能在每次写入时把每一对都交给语言模型判断。

因此，实时检测必须做一件最难的事：**在很小的候选预算里，尽量把真正相关、真正相反的历史证据捞出来。**

这不是普通搜索。普通搜索漏掉一条，用户可能少看到一个答案；冲突搜索漏掉一条，两个互相矛盾的事实可能从此都以“真相”身份服务后续 Agent。

### 4.2 mema 的实时路径

mema 不是整库扫描，而是把新记忆拆成证据单元，再做受限候选召回：

1. 新记忆被拆成局部证据单元并逐单元向量化；
2. 同一条长记忆内部先做单元×单元自相矛盾检查；
3. 每个新证据单元只从历史库 KNN 召回少量近邻；
4. 在进入小模型前，先过滤时间演进、重复、缺少实体/范围依据、没有可提取值差异的组合；
5. 对剩余少量候选做属性—值冲突判断；
6. 检测结果只生成 notice / pending 项，不让小模型直接篡改记忆；
7. 写入本身已经成功时，后处理失败会明确降级，不诱导调用方重试并制造重复。

当前代码中的关键预算是：每个证据单元 KNN `k=5`，写时最多检查 64 个证据单元，并限制实际进入语义判断的 pair 数和作业时间。状态接口会明确暴露 `evidence_units_capped`、`pairs_examined_capped`、`notice_budget_exhausted` 等降级原因，不把“没来得及查完”伪装成“检查过且没有冲突”。

这条设计非常重要：**预算有限不可怕，静默装作全查过才可怕。**

### 4.3 实时召回率应该怎样解读

0.16.6 最初基线中，写时冲突检测对全部冲突形状的 precision 为 75%，recall 为 13.64%。如果脱离上下文看，这个召回率不高；但它测的是一个受 3 秒同步窗口、候选 KNN、证据单元上限、pair 上限和本地 0.5B 模型共同约束的实时路径，并且语料故意混入了本应交给扫描线处理的演进/替代类冲突。

更关键的是，这份低基线已经触发了针对性修复，而不是被当成宣传数字：

- 初始“写时对立形状”只捕获 3/12；
- 通过值对立门、单位归一、属性归一、grounding 修复和确定性直达路径后，同一组提升到 8/12；
- 同时对 12 个噪声/共存负例保持 0 假阳性；
- 剩余多轴复杂冲突明确留给扫描线，而不是继续拉高实时延迟。

因此，报告不应简单写“实时召回只有 13.64%，所以冲突能力弱”。更准确的表述是：

> **mema 已经在写入时承担了一个多数记忆系统根本不做的任务：在有限毫秒/秒级预算内，从千条量级记忆和万级证据单元中尽快发现历史冲突。早期全形状基线召回有限，但写时目标形状已经由 3/12 修到 8/12，且保留低误报；复杂漏检由独立扫描线补齐。**

当前真实运行库进一步说明了问题规模：状态接口显示 826 条可索引记忆被拆成 16,582 个证据单元和同量向量。即使记忆条数尚未超过 1,000，证据检索空间早已是万级。用一次写入的小预算去查这个空间，本身就是困难工程。

这里要区分两种数字：

- “8/12”是修复后特定写时对立形状结果；
- “13.64%”是旧版、全形状、混合任务基线。

两者都不能冒充整个冲突系统的最终召回率。前者证明实时线正在变强，后者证明只靠实时线不够——也正是定期扫描存在的原因。

## 五、实时检测不是孤军作战：mema 有第二道定期扫描防线

如果写入路径不能全库扫描，成熟设计不应假装实时检测万能，而应建立异步补偿机制。mema 已经实现了这条闭环。

### 5.1 全量首扫，之后增量

`scan_pipeline` 由服务端决定全量还是增量：

- 首次运行或检测器语义版本变化：执行全量扫描；
- 后续运行：依据每条记忆的 scan watermark，只扫描新增、编辑、移动或未扫描的记忆；
- 中断后：从断点继续；
- 默认单次 kick 最多处理 400 条记忆、45 秒；
- 每条记忆默认只取 10 个相对近邻；
- 一轮完成后记录 detector version、边界、进度和审计信息。

这像银行的双层风控：刷卡时做毫秒级实时拦截，夜间再跑批量反欺诈。不能因为夜间有批处理就取消实时检查，也不能因为实时有检查就取消夜间盘库。

### 5.2 为什么扫描不是简单地“再搜一遍”

扫描线还包括：

- 同一长记忆内部的自相矛盾检查；
- 同工作区的证据单元相对 KNN 配对；
- 对时间演进、版本变化、计划状态、复述引用等非冲突形状做机器排除；
- 对确定性非冲突自动写入可审计的 `not_a_conflict`；
- 对剩余疑似项进入独立 `scan_queue`；
- 使用版本钉和检测器版本，防止旧判断压住新版本事实；
- 已经裁决的组合不会无故反复骚扰，但内容版本变化后可以重新打开检查。

也就是说，扫描不是“把相似的两句话扔给 Agent”，而是一个带水位、状态机、抑制、重检和审计的持续治理管线。

### 5.3 定时任务与 Agent 自治

mema 本身不常驻一个内部定时器，而是向宿主 Agent 提供平台无关的 scheduled-task 规格。系统会提示：

- 从未扫描；
- 因检测器升级需要重扫；
- 最近扫描已经超过时限；
- 定时任务规格版本过旧，需要重建。

定时任务负责反复 kick，直到本轮扫描完成，再分页清空判断队列。

扫描过程中，高确定性的机器规则可以直接完成治理性清理，例如：

- 明确的数字候选噪声可以自动驳回，并留下审计记录；
- 确定性“无值差异”组合可以 machine-clear；
- 高置信度工作区归位在双信号一致、置信度达到阈值且不触碰受保护空间时，可以由 Agent/服务端执行；
- 严格模式、受保护工作区、低置信度或需要改变事实真值的动作仍然要求授权。

这体现的是**分级自治**，不是“Agent 想改就改”：

```text
确定性机械噪声 ──→ 自动驳回 + 审计
高置信度、可逆、低风险治理 ──→ Agent 自治
事实真值变化 / 受保护内容 / 低置信度 ──→ 用户授权
```

这套能力很超前，因为它同时避开了两个极端：

- 全部让用户确认，最终用户被提示淹没；
- 全部让模型决定，最终事实库被模型悄悄改写。

mema 选择的是：**机器扫地，Agent 整理，人类裁决真相。**

## 六、长文：mema 的优势不是“上下文窗口更大”，而是根本不押注整段向量

### 6.1 整段向量的两个问题

把整篇长文做一个 embedding，存在两类风险：

1. **输入截断**：超过模型或推理框架上限的后半段可能没有进入向量；
2. **语义平均化**：即使没有截断，一篇同时讨论预算、权限、时间、风险的文档，也会被压成一个折中的总体方向，具体条款容易被稀释。

mema 自己的 embedder 源码甚至明确记录：底层 `llama-cpp-python` 的 `embed()` 会按 batch/context 能力静默截断，因此 mema 不假装这个问题不存在，而是把长内容切成局部证据单元，逐单元向量化，并保存原文坐标。

### 6.2 mema 如何处理

- 长内容拆成多个 text evidence unit；
- 每个单元独立 embedding；
- 查询命中的是具体单元，而不是整篇文档的平均向量；
- 返回 `hit_spans` 时带原文 span 坐标，命中片段不静默截断；
- 命中覆盖达到 50% 时可自动升级返回全文；
- 冲突检测也在证据单元层进行，因此能发现同一长文前后自相矛盾。

当前真实库的 826 条记忆拆出了 16,582 个证据单元，平均每条约 20 个单元。这说明“长文本证据化”不是 PPT 上的设计，而是在生产库中实际运行。

### 6.3 mem0 应如何评价

mem0 当前主链路通常不是简单地把整段对话原样 embedding，而是先让 LLM 抽取较短事实，再向量化这些事实。因此不能笼统声称“mem0 永远把全文整段向量化”。

但它仍有三个未证实点：

- 抽取 LLM 面对超长输入时是否完整覆盖后部信息；
- 一篇多主题长文能否稳定抽全细粒度事实和限定条件；
- 官方 LoCoMo / LongMemEval / BEAM 高分是否包含“关键事实埋在超长文档截断区”的专项压力测试。

在已核对的 README、评测说明和 OSS 主链路中，没有找到足够证据证明这三点。因此负责任的结论是：

> **mema 在长文、多主题、限定条件、原文证据和文内冲突方面具有可由源码直接证明的结构优势；它是否在所有长文 benchmark 上整体高于 mem0，仍需同语料双跑，暂不可对外声明具体领先幅度。**

## 七、多模型、多向量库：是可选性，不是质量证明

mem0 支持很多 LLM、embedding 模型和向量库。这对开发者迁移有价值，但不能直接计入“记忆更好”。

因为每次更换 embedding 模型，都会改变：

- 相似度分布；
- top-k 候选顺序；
- 合适的距离阈值；
- 语义与 BM25 融合权重；
- 中英文、长短文本、专有名词的表现。

更换向量库也可能改变距离口径、过滤语义、近似索引误差和一致性。接口跑通只是第一步，重新标定才是第二步，真实回归才是第三步。

mem0 仓库中没有看到覆盖“主要 embedding × 主要向量库 × 主要语言 × 主要数据长度”的完整质量矩阵。因而应分开说：

- **已证实**：mem0 的适配广度更大，开发者选择更多；
- **未证实**：所有组合都保持官方 benchmark 水平；
- **不能推出**：支持的模型越多，最终用户的记忆越准确。

mema 的路线更窄，但它对当前本地 embedding、阈值、分段、召回门和小模型判断做了生产数据校准。比如它已经用真实库推翻过绝对距离带，用相对排名替代；也用真实正负样本重做过写时相似提示阈值。这种“少支持一些，但对实际组合做深测”的策略，对追求稳定的用户可能更有价值。

一句话：**mem0 是插座多，mema 是把一套电路反复测到不跳闸。**

## 八、团队版：上一版比较对象不完整

上一版拿 mema Community/Core 的 localhost HTTP 与 mem0 Self-hosted / Managed Platform 比认证、隔离和多人服务，属于错层比较。

mema Team 是独立的商业/团队分支，已有如下代码与变更证据：

- strict workspace read ACL；
- 显式 workspace 下的跨租户写入阻断；
- pending workspace 确认；
- structured claim 隔离；
- claim revision pin，声明变化可重新触发语义审查；
- arbitration 与 supersede 同事务收口；
- extension runtime 与 trusted context；
- QueryConstraint / compiled memory constraints；
- WriteObserver 与原子写入钩子；
- team grant/provider 接入点；
- enterprise readiness、admin、deep diagnostics、audit 策略；
- deny-all / constrained-runtime 测试。

这些能力说明，mema Team 并不是给个人版简单加一个登录页，而是把约束、授权、观察器、审计和跨租户防护放进写路径和查询路径。

但也必须如实标注：当前可见 Team 分支版本为 `0.1.0-alpha.0`，基于 Core 0.12.5，尚不能仅凭设计清单断言其所有生产指标已经全面超过 mem0 Managed Platform。可以直接断言的是：

- 上一版“mema 不具备团队隔离、认证和多人能力”的判断错误；
- mema Team 的隔离与治理模型更深入地进入了记忆语义和变更事务；
- 两者的吞吐、可用性、认证完整性和大规模租户性能仍需同层实测。

因此，本项修正为：**治理架构倾向 mema Team；生产成熟度与规模性能暂不可对外声明整体胜负。**

---

## 九、能力地图：从“功能多”改成“错误控制深度”

```text
                       高吞吐、低治理成本
                              ↑
                              │      mem0
                              │  抽取 → ADD-only → 混合召回
                              │  依靠排序选择合适事实
                              │
       生态选择多  ←──────────┼──────────→ 事实治理深
                              │
                              │                   mema
                              │  写时查冲突 → 定期扫描
                              │  队列判断 → 分级自治
                              │  授权裁决 → 版本审计
                              ↓
                    高正确性、低静默冲突风险
```

两者不是“一个有召回、一个没召回”，而是主航道不同：

- mem0 优先让记忆容易进入、容易检索；
- mema 优先让错误不容易沉淀、冲突不容易静默。

## 十、按用户价值重新打分

以下不是行业统一分数，而是按“长期可信记忆”目标做的设计评价。

| 维度 | mem0 | mema | 判断依据 |
|---|---|---|---|
| 错误新事实风险 | ADD-only 保留所有抽取结果，错误也会积累 | 写时查重、查冲突、notice、版本与治理 | mema 更强 |
| 历史事实冲突发现 | 主要依靠检索阶段的时间/实体排序 | 写时实时检测 + 定期全量/增量扫描 | mema 明显更强 |
| 冲突后的处理 | 可 update/delete/history，但缺少完整冲突生命周期 | 候选、队列、确认/驳回、治理、版本钉、审计 | mema 明显更强 |
| 长文证据召回 | 依赖抽取质量；未见截断区专项证据 | 证据单元向量、span 坐标、全文升级、文内冲突 | mema 架构更强 |
| 常规个性化召回 | 语义 + BM25 + 实体，多信号融合 | FTS + 局部向量 + 锚点融合 | 无同场实测，暂不判整体准确率 |
| 写入延迟 | 单次抽取，路径较轻 | 写后异步检测，提供短同步等待；复杂度更高 | mem0 更轻 |
| 静默失败控制 | 主要依赖调用异常与结果 | 明确上报截断、预算耗尽、模型不可用、队列溢出 | mema 更透明 |
| 模型/存储可选性 | 广 | 窄而校准深 | mem0 更灵活，但不等于更准 |
| 模型切换稳定性 | 缺少完整组合质量矩阵 | 当前主组合有真实库调参与专项评测 | mema 当前组合证据更扎实 |
| Agent 自治治理 | 非核心主线 | 定时扫描、机器排噪、高置信低风险自治、事实变更授权 | mema 更强 |
| 团队隔离与审计 | Self-hosted/Platform 有认证与作用域 | Team 有 strict ACL、跨租户写阻断、constraint、observer、audit | 架构上 mema 更深；成熟度待同层实测 |
| 标准公开 benchmark | 更完整，托管版成绩高 | 自建真实库专项测试更多，标准集不足 | mem0 的公开证明更强 |

## 十一、测试数字应该怎样诚实使用

### mem0

官方 README 报告：

- LoCoMo 92.5；
- LongMemEval 94.4；
- BEAM 1M 64.1；
- BEAM 10M 48.6。

这些结果证明 mem0 团队有成熟的标准评测能力。但官方同时说明：成绩来自包含专有优化的 Managed Platform，OSS 用户只能期待方向相似，不能期待相同结果。

### mema

0.16.6 通用召回基线：

- Recall@5：82.22%；
- Recall@10：95.56%；
- MRR：0.797；
- 自召回 Top10：98.98%。

冲突检测不能只引用旧的 13.64%：

- 旧版全形状写时基线：precision 75%，recall 13.64%；
- 旧版目标写时对立形状：3/12；
- 修复后同一目标形状：8/12；
- 修复验证负例：12 个噪声/共存样本，0 假阳性；
- 更复杂的演进、多轴冲突明确交给扫描线。

真实库运行状态：

- 826 条可索引记忆；
- 16,582 个证据单元；
- 16,582 个向量；
- 冲突扫描已有 full/incremental 水位、检测器 epoch 和定时任务规格记录。

这些数字能证明 mema 在真实库上运行过复杂治理链，但不能与 mem0 的 LoCoMo 分数直接相减。

## 十二、最终判断：排除用户数量，哪个更好

如果评价目标是“接入快、SDK 多、存储任选、快速给聊天机器人加记忆”，mem0 仍然有吸引力。

但用户问的是“哪个更好”，而长期记忆最重要的不是记得多，是别记错；不是搜得快，是别把错的搜出来；不是模型任选，是换完模型质量别漂；不是冲突都留着，是冲突出现后有人负责。

按这个标准，我的结论是：

> **mema 更好。**

不是因为它功能表更长，而是因为它处理了记忆系统最棘手、最容易被忽略的问题：

- 新写入也可能是错的；
- 历史事实会冲突；
- 实时检查不可能全库扫描；
- 有限候选必然漏检；
- 漏检需要定期扫描补偿；
- 扫描结果需要分级自治；
- 真值修改必须授权；
- 每次治理必须可追溯。

mem0 的 ADD-only 是一种高效策略，但也是一种风险转移：把写入时的事实判断，转移到未来每次检索。mema 则承认没有任何单次模型判断可靠到足以统治事实库，于是用实时检测、定期盘库、Agent 判断、用户授权和版本审计组成多道防线。

打个比方：

- mem0 像一个速度很快的仓库，任何新箱子都先收下，发货时再找最像正确货物的那箱；
- mema 像一个带验货、批次、盘点、异常单和审批制度的仓库。入库慢一点，制度重一点，但不让两箱互相矛盾的“真货”长期静默共存。

对娱乐聊天，前者可能更轻；对工作记忆、团队知识、多 Agent 协作和长期事实，后者更值得信任。

## 十三、仍然不能对外夸大的地方

支持 mema，不等于替 mema 掩盖缺口：

1. 没有同语料 head-to-head 前，不能宣称 mema 的常规问答准确率一定高于 mem0 多少个百分点；
2. 长文架构优势可以直接声明，但实际领先幅度仍需专项双跑；
3. Team 当前可见分支仍是 alpha，不能仅凭架构就宣传大规模生产成熟度全面领先；
4. 写时冲突检测不是全库扫描，必须继续诚实展示预算和降级状态；
5. 定期扫描要依赖宿主 Agent 正确安装并持续运行定时任务，doctor/spec-drift 提醒虽已补上，仍应测长期执行可靠性；
6. mema 的标准公开 benchmark 和外部复现仍少于 mem0，这是证明能力的真实缺口。

中立不是各打五十大板。中立是：优点必须说明代价，缺点必须放回工程约束里解释，结论必须跟证据强度一致。

## 十四、建议补做的三组同场测试

### 1. 错误新事实测试

构造 200 组“旧事实正确、新写入错误/假设/转述/口误”的对话，测试：

- 错误写入率；
- 冲突发现率；
- 后续查询选错率；
- 治理后复发率。

这是 ADD-only 与治理式记忆最核心的正面对决。

### 2. 长文截断与多主题测试

每篇 5K、20K、50K、100K 字，关键信息分别放在开头、中间、末尾；加入限定条件、表格、否定句和文内自相矛盾。比较：

- 关键事实 Recall@5/10；
- 截断区召回率；
- 限定条件完整率；
- 原文证据可定位率；
- 文内冲突发现率。

### 3. 千条库实时冲突 + 定期扫描联合测试

在 1K、5K、10K 条记忆规模下，分别测：

- 写时检测 recall / precision / p50 / p95；
- 每次写入候选数量和 Qwen 调用数；
- 未被实时发现的冲突，有多少在下一轮扫描补回；
- 从写入到最终治理的端到端召回率；
- 自动驳回、Agent 自治、用户授权三类处理的正确率；
- 扫描中断、模型不可用、检测器升级后的恢复能力。

真正公平的指标不是“写时一次抓到多少”，而是：

> **实时线不拖慢写入的前提下，实时检测 + 定期扫描 + 治理闭环，最终能消灭多少静默冲突。**
